# Consumers // design-system-ASK

Known **landed** consumers of [design-system-ASK](README.md) patterns and tokens — the **public downstream repos** below, plus design-system-ASK's own **first-party same-repo** consumers (its three public surfaces, and its pattern-preview gallery).

This file records **landed consumption only** — which repo or first-party surface already consumes which pattern or token module. It is a transparency record, not a customer list, not the full propagation ledger, and not a future-state plan. Queued, in-flight, or planned consumption, private/firewalled consumers, **vendored commit pins**, re-sync obligations, and pin drift are tracked operator-side, not here, by design — a pin is operational provenance and does not belong in the public registry.

Two lifecycles govern how these patterns are inherited, and they are not interchangeable.

**Artifact scaffolds** are inherited at generation time. A downstream consumer vendors the complete canonical artifacts for the modules it actually renders, then generates its own output, seals it, stamps it where the pattern requires, and freezes it for audit. That consumer owns its source data, chrome, generation, sealing, and frozen artifact; design-system-ASK owns the engine, CSS, and export script.

**Surface patterns** frame a live deployed surface. A consumer takes one by same-repo reference or as a pinned local vendored copy, and nothing seals — the page keeps running, and the consumer re-syncs when the owner contract changes. Tier 3, payload, deployment, and local instance adaptations stay with the consumer; design-system-ASK owns the shared pattern contract and its canonical CSS.

Neither lifecycle uses a CDN or a live hot-link. Ordinary downstream diagram / artifact consumers take the foundations through their local, pinned `_dsa-tokens/` mirror; the ASK front door vendors the foundations (tokens, fonts, wordmark) directly rather than via a `_dsa-tokens/` mirror (see its row below). Re-sync is the downstream consumer's responsibility when an upstream pattern or token module changes.

## First-party consumers

Same-repo consumers, distinct from the public downstream repos above: they consume the canonical bundles by **same-repo reference**, not a vendored `_dsa-tokens/` mirror. There is no vendored pin and no copied bundle, and referenced canonical assets resolve at repo `HEAD`. Two different relationships live here, and they do not share a maintenance verb.

**Live first-party surfaces** consume the canonical assets by direct same-repo reference. When an owner contract changes they need rendering and behavior verification, not regeneration — a page does not rebuild its chrome because the stylesheet it references changed.

**Generated preview artifacts** are regenerated and reverified from their canonical pattern sources, through generator `--check`, generated-set parity, and visual verification. That is a separate relationship from a page consuming `surface-shell` for its own chrome.

Operational currency is tracked operator-side, as for public consumers.

## Vendoring granularity

**Shared contract, selective renderer.** The diagram source grammar and the `window.DIAGRAMS.render(TREE)` interface are a *shared contract*, uniform across the static pattern family, so source data is portable between engines. The concrete pattern engines (`diagram-static-{H,V,SEQ,FLOW}`, `diagram-interactive-spine`) are *renderer capacity* — the code a consumer actually runs.

Downstream consumers vendor the complete canonical artifacts for the patterns/modules they **actually render**. Optional capabilities inside an adopted module travel with that module, even if unused, and must not be cherry-picked or locally forked. Unused pattern engines are **not** pre-vendored speculatively; a consumer adopts and vendors the *current* canonical engine when it first renders that pattern. Shared artifacts — the static exporter, the token mirror — remain whole shared artifacts, not split by dormant internal branches. The vendoring boundary traces the code seam: selective by pattern where engines diverge, whole where an artifact is genuinely shared — which keeps each consumer's re-sync obligation to exactly the patterns it exercises.

## What this file is not

- **Not a customer or marketing list.** It records implementation relationships — public downstream repos and design-system-ASK's own first-party same-repo surface — nothing more.
- **Not the full propagation ledger.** Queued / in-flight consumption, private/firewalled consumers, vendored commit pins, re-sync obligations, and pin drift are tracked operator-side, outside this public repo.
- **Not a currency guarantee.** Listing a consumer here does not assert it tracks the latest upstream; a downstream consumer may lag until it re-syncs, and the first-party generated preview set until it is regenerated and reverified. Specific vendored pins and currency are operator-side provenance, deliberately not published here.

A private operator-internal consumer has also exercised the Class B `output-artifact` flow end-to-end; its contents remain firewalled and it is not listed here.
