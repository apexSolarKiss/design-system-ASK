# Pattern // diagram-static-peer

A reusable static-artifact scaffold for **peer relations**: three or four equal peers on a regular polygon, joined by declared relations, that inherits the [design-system-ASK](../../README.md) visual language. It has two presets, which fix placement only: a **triangle** of three positions and a **square** of four. Each ships a template: the triangle's joins its three peers in a clockwise directed cycle, and the square's joins four by a clockwise directed perimeter with its opposite pairs neutral. Every plate is neutral unless its spec is a **declared semantic example**, an opt-in that applies Criterion Assessment or Three Functions to its nodes ([below](#declared-semantic-examples)).

This is a **Class A static** diagram scaffold, distinct from the **Class B** project-output artifact patterns. Its static siblings — [`patterns/diagram-static-H/`](../diagram-static-H/README.md), [`-V/`](../diagram-static-V/README.md), [`-SEQ/`](../diagram-static-SEQ/README.md) and [`-FLOW/`](../diagram-static-FLOW/README.md) — arrange hierarchy, succession and convergence, and share the `window.DIAGRAMS.render` interface and one PNG exporter. This pattern arranges peers. It has its own relation grammar, engine and exporter, and takes none of their chrome, fit, pointer or text-layout carriers: a fixed plate of three or four letters has no canvas to pan and no label to wrap. The surface pattern [`patterns/diagram-interactive-radial/`](../diagram-interactive-radial/README.md) arranges a containment hierarchy on a live page; this one arranges equals on a sealed plate.

## What this pattern is

A plate is a 1000-unit square: the foundation's 45-degree gradient field, one letter at each vertex inside an outlined ring, and a connector for each declared relation. Every ring has the same size and stroke. On a plate that is not a declared semantic example, which includes every template and every neutral instance, the ring is one neutral outline in the plate's ink, lighter than a letter's strokes and heavier than a connector, with no fill: it encloses the node and carries no state, emphasis or selection. A declared semantic example fills a ring only as [Declared semantic examples](#declared-semantic-examples) states. A **directed** relation is a line with a filled, slightly notched head at its target. A **neutral** relation is a fitted dash with no head, lighter than a directed one, so two neutral diagonals cross as lines and never as a node. Every connector stops the same gap outside the rings it joins: a neutral line begins and ends on dash ink at that gap, as a directed line and its head do. The **keyed** plate adds a band under the polygon: a drawn sample of each relation type the plate uses, with the instance's own word for it.

The spec owns the content: the labels, which pairs relate, the words for each relation and, in a declared semantic example, every assignment and explanation. The engine owns placement, connectors and presentation, and reads no meaning into a relation beyond its type. A-S-K and L-E-O-V are ASK's instances, read as a game; the templates carry numbered slots and no reading.

Eight files:

- `README.md` // this file
- `diagram-static-peer.html` // the specimen: the instances, the neutral-opposites square beside the all-directed square, the templates, a relabeling, the two declared semantic examples and the checks, drawn from the relation sources
- `diagram-static-peer.source.js` // the relation sources the specimen draws, as one `window.PEER_DIAGRAMS` array: six neutral specs and two declared semantic examples
- `diagrams-static-peer-engine.js` // **DS-owned engine** (`window.DIAGRAM_PEER`, or a Node module): validation, the derived checks, and the renderer, a pure function from a spec to a standalone SVG string. The page and the exporter run the same code
- `diagrams-static-peer.css` // the specimen's column, figure grid, plate frame and two mode selectors. Its text takes the document register
- `diagrams-static-peer-glyphs.js` // **DS-owned, GENERATED** by `tools/gen-peer-font.py` from `fonts/InterVariable.woff2`: each supported label's measured centering and the radius its centered ink reaches (`r`, rounded up from every outline point, so it never understates the ink), and each printable Basic Latin character's advance at the key's weight, which a declared semantic example's notes and band share. Never hand-edit it
- `diagrams-static-peer-font.js` // **DS-owned, GENERATED** by the same tool: Inter subset to printable Basic Latin, with the `wght` and `opsz` axes kept, as a base64 `@font-face` rule, with Inter's copyright and the SIL Open Font License text. Only the exporter loads it
- `export-peer.mjs` // **DS-owned exporter** (Node 18 or later, no dependency): writes each spec as standalone SVG files and, on request, PNG files

**Load order is a contract.** The page loads the stylesheets `colors_and_type.css → surface-text-link.css → surface-panel.css → surface-document.css → surface-treatments.css → spectral-state.css → criterion-assessment.css → three-functions.css → diagrams-static-peer.css`, then the scripts `<source> → diagrams-static-peer-glyphs.js → diagrams-static-peer-engine.js`, then its own script. A page that draws no declared semantic example may leave out `surface-panel.css`, `surface-treatments.css` and the three systems' stylesheets. A page that draws one needs `surface-panel.css` then `surface-treatments.css`, for the inks, and its system's stylesheets: `spectral-state.css` then `criterion-assessment.css`, or `three-functions.css`. Without them an example's colored rings and letters take the host's inherited fill, which is black unless the host sets one: vendor them with the engine, from one design-system commit. The engine reads nothing global: the page passes it the glyph carrier, and `render` fails closed rather than centering letters by guesswork: without one, `GLYPHS_MISSING`; with one whose letter offsets, ink radii or measured weight are not finite numbers, or whose ink radius is negative, or that lacks a finite, non-negative advance for a printable Basic Latin character, `GLYPHS_MALFORMED`.

The pattern is **not** a component library, a generator, a build pipeline, an npm package or a project-specific diagram. It is a starting point for downstream peer diagrams that consume design-system-ASK foundations.

## The relation contract

```text
spec = {
  id:         letters, digits, '.', '_' and '-'           'triangle.A-S-K'
  preset:     'triangle' | 'square'
  role?:      free text for the page; the engine ignores it
  title?:     the plate's accessible name, with no control character; defaults to id
  nodes:      [{ id, label }, ...]  clockwise from the preset origin:
              the triangle's top, the square's upper left
  relations:  [{ from, to, type }, ...]  every pair exactly once
  meaning?:   { directed?, neutral?, verb?, neutralPlain? }
  semantic?:  { system, ... }   only on a declared semantic example (below)
}
```

On a declared semantic example a node is `{ id, label, assessment, figure? }` for Criterion Assessment, or `{ id, label, function, does? }` for Three Functions.

- **Nodes.** A triangle takes three nodes and a square four. A node id starts with a letter and continues in letters, digits, `_` or `-`. A **label** is one character, `A`–`Z` or `0`–`9`: the glyph carrier measures the ink of exactly these, so every letter sits centered on its vertex and clear of its ring. Labels are distinct.
- **Relations.** Every pair of nodes is declared exactly once, in either orientation. `directed` reads *from → to* and draws its head at `to`. `neutral` draws the dash. `unspecified` declares a pair open and draws nothing. **An undeclared pair is an error, never a neutral pair**: completeness is explicit, and `unspecified` is the one way to leave a pair open. The shipped relation sources — the templates, the instances and the specimen's comparison and relabeling — run every directed cycle clockwise, the order their labels read, and list its relations in that order, which the plate's description and the specimen's captions follow. That is a convention of these sources, not a rule of the engine, which draws whichever direction a spec declares.
- **Meaning.** The instance's own words, all optional and all printable Basic Latin, the range the exported font covers. `directed` and `neutral` label the key's samples; each must fit its slot, measured against the key's advance widths. `verb` joins *X verb Y* in the plate's description (default `to`), and `neutralPlain` phrases *X and Y neutralPlain* (default `are neutral`). The engine reads no meaning from any of them.
- **Closed fields.** A spec, a node, a relation, the meaning and the options each accept only the fields above. A misspelled field is an error, not an omission. `semantic`, and a node's `assessment`, `figure`, `function` and `does`, are accepted only as [Declared semantic examples](#declared-semantic-examples) states: on a neutral spec, or of the other system, a node's assignment is `NODE_KEY`.
- **Every entry is read.** The nodes and relations are read at every index, so a hole in either array is an entry that is not an object, never one that is skipped.

`validate(spec, glyphs)` never throws: it returns `{ ok, errors }`, each error a `{ code, path, message }`, and a spec whose fields cannot even be read is `SPEC_UNREADABLE`. `render` throws a `PeerError` carrying `code` and every error. Membership tests are exact: a relation type, a node id or a preset is matched against its own declared set, so a name every object inherits, such as `constructor` or `toString`, is an ordinary unknown value and never passes as one that exists.

| Code | Raised when |
| --- | --- |
| `SPEC_NOT_OBJECT` · `SPEC_UNREADABLE` · `SPEC_ID` · `SPEC_KEY` · `SPEC_ROLE` · `SPEC_TITLE` | the spec, its id, its title or its fields are malformed, or the spec cannot be read |
| `PRESET_UNKNOWN` | the preset is not `triangle` or `square` |
| `NODES_NOT_ARRAY` · `NODE_COUNT` · `NODE_NOT_OBJECT` · `NODE_KEY` · `NODE_ID` · `NODE_ID_DUPLICATE` | the nodes are malformed, too many or too few, or repeat an id, or a node carries a field its spec does not accept |
| `LABEL_UNSUPPORTED` · `LABEL_DUPLICATE` · `LABEL_UNMEASURED` · `LABEL_RING_FIT` | a label is not one of `A`–`Z`, `0`–`9`, repeats, has no measured centering, or its measured ink would leave less than the ring's padding clear inside its ring |
| `RELATIONS_NOT_ARRAY` · `RELATION_NOT_OBJECT` · `RELATION_KEY` · `RELATION_TYPE` · `RELATION_ENDPOINT` · `RELATION_SELF` · `RELATION_PAIR_DUPLICATE` | a relation is malformed, has an unknown type or endpoint, relates a node to itself, or repeats a pair |
| `PAIR_UNDECLARED` | a pair has no relation |
| `MEANING_NOT_OBJECT` · `MEANING_KEY` · `MEANING_TEXT` · `MEANING_KEY_WIDTH` | the wording is malformed, outside printable Basic Latin, or too wide for its key slot |
| `SEMANTIC_NOT_OBJECT` · `SEMANTIC_SYSTEM` · `SEMANTIC_KEY` · `SEMANTIC_DECLARATION` · `SEMANTIC_TEXT` · `SEMANTIC_TEXT_WIDTH` · `SEMANTIC_BAND` | `semantic` is not an object, names no supported system, carries a field its system does not declare or lacks one it does; a declaration is not a list of lines of printable Basic Latin, or a line is too wide for the band; or the band would take more lines than it holds |
| `NODE_ASSIGNMENT` · `NODE_TEXT` · `NODE_TEXT_WIDTH` | a node of a declared semantic example lacks its assignment or gives one outside its system's set; its `figure` or `does` is not a list of lines of printable Basic Latin, a figure runs past two lines, a role-bearing node gives no `does` or a node of no function gives one; or a line is too wide for its slot |
| `OPTIONS_NOT_OBJECT` · `OPTION_KEY` · `GLYPHS_MISSING` · `GLYPHS_MALFORMED` · `OPTION_THEME` · `OPTION_KEYED` · `OPTION_ARROWHEADS` · `OPTION_ID_PREFIX` · `OPTION_FONT_FACE` · `OPTION_METADATA` | a render option, or the glyph carrier, is malformed or missing; a title, the metadata or a theme value carrying a character XML forbids, or markup or CSS punctuation in a theme value, is among them; and so are an art plate asked of a declared semantic example (`OPTION_KEYED`), and a resolved theme that lacks its system's roles or carries a malformed one (`OPTION_THEME`) |
| `MOUNT_HOST` | `mount` is given no element |

The derived checks read only the declared relations: `matrix` (1 for *row → column*, −1 for the reverse, 0 neutral, `null` unspecified), `signatures` (each node's outgoing, incoming, neutral and unspecified partners), `symmetry` (the rotations that carry the pattern onto itself) and `describe`. They are structural: no score, payoff or ranking belongs to them. A reading such as the specimen's game is the instance's, and so is every assignment in a declared semantic example.

## Declared semantic examples

The default plate is neutral, and a template is never anything else. A spec may instead be a **declared semantic example**: `semantic` names one opt-in system, every node carries that system's assignment, and the plate shows everything a reader needs to read the color. Only the spec's own `semantic` declares one: a spec that inherits it validates, draws and exports as the neutral plate. `semanticSystem(spec)` returns the declared system's name, or `null`, by the rule `render` applies; the exporter and the specimen page use it. An example applies one system: no plate carries both, and no node takes a function and an assessment.

- **Criterion Assessment.** `semantic: { system: 'criterion-assessment', criterion, direction, scope, basis, rule }`: the criterion, which direction is better, what is compared, where each value comes from, and the threshold rule, or that the ratings are an author's own, carried as they are. Every node declares `assessment`: `favorable`, `caution`, `adverse` or `unassessed`, and may give a `figure` of one or two lines. An assessed node's ring is filled at 100% of its role's value, its boundary in the same value, and its letter takes the role's ink: the profile's [filled-node application](../../criterion-assessment.md#the-filled-node-application). Beside it, outside the ring, the plate draws its figure and then its assessment word, in the plate's ink. An unassessed node keeps the neutral ring and draws no word; a figure it gives stays beside it as plain text, and none is invented.
- **Three Functions.** `semantic: { system: 'three-functions', scope }`: what the plate depicts. Every node declares `function`: `legislative`, `executive` or `judicial`, admissible under the primitive's rules, or `none` for a node that performs no function, which keeps the neutral ring and draws nothing beside it. A role-bearing node gives `does`, what it does in this example; a `none` node gives none. A role-bearing ring is filled in its role's value with its letter in the role's ink, the executive white in light and lavender in dark, as [Three Functions](../../three-functions.md) resolves it, and the function's name sits beside the node in the plate's ink.

**Text fields.** `system`, `assessment` and `function` are strings from their closed sets. Every declaration, `figure` and `does` is a list of one or more lines of printable Basic Latin, the range the exported font covers. The free-text `role` and the `meaning` fields are unchanged. The engine sets each line as declared and wraps nothing. A declaration's line or a `does` line must fit the band's text column, 542 units at a size of 32; a figure's line must fit its note, 360 units at 34. Each is measured as the unkerned sum of the key's advance widths, which the glyph carrier measured at the weight and optical size these sizes draw at; kerning moves a drawn width by little, and the host-inheritance test confirms every line stays inside the plate. A band holds 18 lines.

**The notes and the band.** Each node's note is centered on its vertex, above a node in the plate's upper half and below one in its lower half. Under the key, the band draws the system's name, then each declaration under its label and, for Three Functions, each role-bearing node's `does` under its letter and function, all in the plate's ink. The plate grows by the band.

**Keyed only.** A declared semantic example is drawn and exported with its key and band, because both are part of reading its color: for an example `keyed` defaults to `true`, and `keyed: false` is `OPTION_KEYED`. The art plate stays every neutral spec's.

**What it changes, and what it does not.** The assignments are the example's content: the engine infers none from a label, a position or a relation, and they change no relation, matrix, signature or symmetry. An example's connectors, heads, key, rings and letters sit exactly where a neutral plate of the same relations puts them. The plate's description adds each node's assignment and the example's declarations. A missing or unknown assignment, or a missing declaration, is an error, never a default. The page and the exporter draw an example by the same path.

**Paint.** With `theme: 'inherit'` a colored ring reads `--assessment-<role>` or `--function-<role>`, and its letter `--assessment-<role>-ink` or `--function-<role>-ink`, from the page: each system binds its roles to their colors, and the surface treatments' FILL PAINT keys each ink by its color. A resolved theme carries the same values as `roles`, which the exporter resolves from those stylesheets. The engine applies FILL PAINT's recipe itself, the ring at 100% of its role's value, its boundary in the same value and its letter in the ink FILL PAINT keys by that value, in rules scoped to the plate, so a page plate and a standalone file draw by one path. The inheritance protections below apply to those rules, within the limits stated there; a host's rule written against the plate's own elements, or one marked `!important`, remains outside that guarantee. The plate carries no `.surface-fill` class, and so takes no `--surface-fill-edge`. The engine names no color and takes none from a spec: there is no color input beyond the systems' own roles.

The specimen's two examples are ASK's: A-S-K assessed against one assumed opponent mixture, and L-E-J in a fictional design commission. Their assignments and words are theirs, not the letters': the neutral A-S-K instance keeps its game and no assessment.

## Rendering

`render(spec, options)` returns one standalone `<svg>`:

- **`glyphs`** // required: the `DIAGRAM_PEER_GLYPHS` carrier.
- **`theme`** // `'inherit'` (default) draws with the page's foundation roles — the field from `--bg-from` and `--bg-to`, ink from `--fg-1`, letters in `--font-sans` at `--fw-extralight`, the key at `--fw-regular` — so a plate on a page follows the page's theme; a declared semantic example also reads its system's role and ink tokens. A **resolved theme object** — `{ name, fieldFrom, fieldTo, ink, fontFamily, labelWeight, keyWeight, roles? }` — draws a standalone file with those values written in. Its `labelWeight` must be the weight the glyph carrier measured the letters at, or they would sit off center. `roles` is a declared semantic example's: each of its system's three colored roles, and no other, as `{ fill, ink }`, resolved color values like the others, with no quote. It must be the theme's own property: a `roles` the theme only inherits is not its roles, so an example drawn with it is `OPTION_THEME`, as with no `roles`, and a neutral plate ignores it. `render` draws each role from the value it checked, read once. A neutral plate's theme takes no `roles` of its own.
- **`keyed`** // `false` (default) is the art plate; `true` adds the key band, 150 units, with one item per drawn type. A declared semantic example is keyed by default, adds its band below the key, and refuses `false`.
- **`arrowheads`** // **`'target'` is the default, the canonical presentation and the standard export.** `'midpoint'` is a comparison mode: each head sits at its connector's midpoint, and where two directed connectors cross there, as on the all-directed square's diagonals, each head slides toward its own target so the crossing never reads as a node.
- **`idPrefix`** // every element id in the plate begins with it, and every rule in the plate's `<style>` is scoped to it. It defaults to `idPrefixFor(spec.id)`, an encoding under which distinct texts never share a prefix. A plate carries three ids: the prefix itself, `<prefix>_title` and `<prefix>_field`. On a page, **`mount(host, spec, options)`** takes a prefix none of whose three ids any element in the document carries, so the same spec can appear any number of times, beside plates rendered with prefixes of their own; a caller that names its own prefix keeps all three unique. The exporter gives each file a prefix of its own, so exported files can be inlined on one page; the `@font-face` rule they embed declares `Inter`, which joins a host page's Inter for the characters it covers.
- **`fontFaceCSS`**, **`metadata`** // embedded in a standalone file.

Each plate is `role="img"`, named by its `<title>` and described by a `<desc>` derived from its relations. Heads are drawn as paths, not SVG markers, which rasterize unreliably. Each text rule states, rather than inherits, its anchoring — the letters centered on their measured ink, a declared semantic example's notes on their vertex, the key's wording and the band's lines from their start — and these properties, any of which a host could otherwise use to move a text, change the face that draws it or extend its ink: baseline, direction, writing mode and orientation, white space, the face's style, width, variants, size adjustment and optical sizing, kerning, features and variations, letter and word spacing, case, and the stroke and shadow of text; synthesis is off, and heads and the field take no stroke. Each is stated at the value the plate draws with on its own — the subset's kerning on, white space collapsed as an SVG text's is — so a plate looks as it did, and one mounted or inlined under a host's inherited styles draws the same; [`tests/peer-host-inheritance.mjs`](../../tests/peer-host-inheritance.mjs) measures this in Chrome. Text rendering is left to the page: the foundation sets it on its pages on purpose. In Chrome an inherited `optimizeSpeed` turns kerning off in a line drawn with the page's own Inter: it lengthened one band line of the Three Functions example, mounted on the page, by about one unit of its 1000, inside the plate. The exported files, drawn with their embedded subset, did not move. The guarantee covers inheritance, and only the properties stated: a stylesheet rule written against the plate's own elements, or one marked `!important`, is outside it, and so are text rendering, any other inherited property the rules do not state (`-webkit-text-security`, for one), the stroke styles the plate does not set — dashes on its solid connectors and rings, joins and miters — and paint opacity. A page plate takes its family, weights, ink and field from the page's foundation roles; on a page without them, the family and weights fall back to what the host inherits, the letters and heads, and a declared semantic example's colored rings, take the host's inherited fill, which is black unless the host sets one, the field's gradient stops fall back to black, and the rings and connectors take the host's inherited stroke, which is none unless the host sets one. The geometry — the circumradius, the letter size, the node ring (its radius, stroke, the padding it keeps clear around every supported letter's ink, and the gap outside it where connectors stop, from which the clearance is derived), the stroke widths, the fitted dash, the head's dimensions, the key's layout and a declared semantic example's notes and band — belongs to the pattern and is not an option.

## The specimen

`diagram-static-peer.html` draws every spec in the source. It follows the system's light or dark setting and has **no theme selector**. Its two mode selectors are quiet pills that report their state, the [style guide](../../preview/styleguide.html)'s selector grammar:

- **view** // `art plate` or `with key`. With the key, the instances also show their relation tables.
- **arrowheads** // `at target` (default) or `at midpoint`, for comparison.

Nothing is stored: the page always opens at the art plate with heads at the target. The two declared semantic examples are drawn with their key and band in either view. The page's text takes the document register, and the checks table is derived from the relations when the page loads.

## Export

```text
node export-peer.mjs --out <dir>          every spec: art plate and keyed (an example keyed only), light and dark, SVG
node export-peer.mjs --out <dir> --png    the same, plus a PNG of each SVG
```

`--tokens <file>` names the token file (default `_dsa-tokens/colors_and_type.css` beside the script), `--semantic-css <file>` a stylesheet a declared semantic example's roles resolve from (repeatable, in load order), `--source <file>` the relation sources, `--spec <id>` one spec (repeatable), `--arrowheads midpoint` the comparison mode, `--chrome <path>` the browser and `--scale <n>` the PNG's pixels per unit (1 to 4). From this repository's root, pass `--tokens colors_and_type.css` and, for the declared semantic examples, `--semantic-css` for `surface-treatments.css`, `spectral-state.css`, `criterion-assessment.css` and `three-functions.css`, in that order.

- **Files.** `<spec>_<plate|keyed>-<light|dark>.svg`, and the same name in `.png`. A declared semantic example is written keyed only, as `<spec>_keyed-<light|dark>.svg`. Both themes are always written, each with the `-light` or `-dark` suffix that Theme by embedding surface below names. Write each sealed generation to a directory of its own: the exporter overwrites a file of the same name, and the names carry no source or render version. A file's `<metadata>` records the token file's and the font subset's sha256, but not the relation source or the engine revision, so it is not a manifest to reproduce the file from: keep each sealed generation's sources and carriers with it.
- **Tokens.** For each theme the exporter resolves `--bg-from`, `--bg-to`, `--fg-1`, `--font-sans`, `--fw-extralight` and `--fw-regular` from the token file, following `var()` references, and writes the values into the file. It reads the light values on `:root` and the dark overrides on the rule whose selector list includes `:root[data-theme="dark"]`, which must declare the field and the ink itself, so a dark file never borrows a light value. It fails rather than guess on a name that does not resolve, an unbalanced block or an unclosed comment. Each file records the token file's sha256.
- **Roles.** For a declared semantic example the exporter reads its system's stylesheets after the token file, in load order — each `--semantic-css`, or by default `_dsa-surface/surface-treatments.css` and then `_dsa-tokens/spectral-state.css` and `criterion-assessment.css`, or `three-functions.css`, beside the script — and resolves each colored role's `--assessment-<role>` or `--function-<role>` and its `-ink` for each theme, the same way. A later stylesheet's declaration of a name replaces an earlier one, as on a page. An example's file records the sha256 of each stylesheet its roles resolved through, and no other: a Criterion Assessment file names `surface-treatments.css` and `criterion-assessment.css`, whose roles bind the foundation's colors directly, a Three Functions file `surface-treatments.css` and `three-functions.css`, whatever else the run was given. A stylesheet that cannot be parsed is named in the error. The exporter carries no copy of a color: a stylesheet it cannot read, or a role that does not resolve, writes nothing.
- **Font.** Each file embeds the Inter subset, so its letters and key resolve with no font installed, and carries Inter's copyright and the full SIL Open Font License 1.1 text in `<metadata>`. Subsetting is permitted because Inter declares no Reserved Font Name.
- **Checked first.** Every spec the run exports is validated, and every declared semantic example's roles resolved, before any file is written, and the run is refused if a spec id is given twice or two differ only in letter case, such as `Triad.ASK` and `triad.ask`: a file system that ignores case, as macOS's and Windows' do by default, would store their files as one, the later replacing the earlier. Each of these failures writes no files. A failure once writing has begun — no browser found for `--png`, for example — leaves the files already written in place: a run that finds no browser writes the SVGs and no PNG.
- **Determinism.** In one runtime the SVG is a pure function of the spec, the options, the token file, a declared semantic example's stylesheets and the carriers: two runs write the same bytes, and nothing in a file records the time.
- **PNG.** `--png` rasterizes each SVG with headless Chrome or Chromium at the SVG's own size times `--scale`, and checks the PNG's dimensions. The browser is `--chrome`, else `$CHROME`, else the platform's usual install paths (macOS, Windows) or `google-chrome`, `chromium` and `chromium-browser` on `PATH`; with none found it stops and names the paths it tried.

**What is checked, and what is not.** `tests/peer-contract.test.mjs` checks the SVG export on every run: the files written, their determinism, the embedded subset, the license text and the resolved tokens. It also checks the declared semantic examples: every malformed declaration, assignment and line, the plate's paint, notes and band, the keyed-only rule, and the roles the exporter resolves. Paired controls run a spec that only inherits a declaration through the exporter, and a malformed or quote-bearing role mapping given as the theme's own property and as one it inherits. When the pattern was admitted, the plates were also rendered in Chrome and the PNG route was run on macOS with Google Chrome, and so were the semantic examples when they were added; neither is part of the test. `tests/peer-host-inheritance.mjs` renders every exported file in headless Chrome, beneath a control host and beneath hosts with inherited styles, and compares where each text draws and which face draws it; it also mounts each declared semantic example on the page and reads the paint of its colored rings and letters. Not tested: the PNG route on Windows or Linux, and how other editors — Illustrator, Inkscape, Figma — import a file with live text, an embedded variable-font subset and CSS rules in `<style>`. Treat import into an editor as unverified.

### Theme by embedding surface

Every diagram package generates and retains both theme variants (`-light` and `-dark`). The embedding surface selects the default:

- **Repository documentation and operator-system diagrams default to dark.**
- **Substack and other published long-form editorial diagrams default to light.**
- A stated local exception may override the default for a specific figure.

This rule selects which existing render is embedded. It does not suppress, rename, or replace the alternate-theme export.

## The generated carriers

`tools/gen-peer-font.py` writes `diagrams-static-peer-glyphs.js` and `diagrams-static-peer-font.js` from `fonts/InterVariable.woff2`; `--check` regenerates them in memory and fails on any difference. It is owner-only and needs fontTools and brotli, which nothing else in this repository uses; another version of either may subset to other bytes, which `--check` reports. Each carrier records the source font's sha256, and `tests/peer-contract.test.mjs` fails when the canonical font changes and the carriers were not regenerated. A consumer vendors the carriers and never runs the tool.

## How to use it

1. Copy the pattern's files, except this README if you wish, into your consuming project, beside each other.
2. Sync `colors_and_type.css` and the fonts from design-system-ASK into a local `_dsa-tokens/` mirror, and `surface-text-link.css` and `surface-document.css` into a `_dsa-surface/` mirror, pinned to a known upstream commit. The page expects both mirrors beside it. To draw a declared semantic example, also sync `surface-panel.css` and `surface-treatments.css` into `_dsa-surface/`, and `spectral-state.css`, `criterion-assessment.css` and `three-functions.css` into `_dsa-tokens/`, from the same commit; a page that draws none may drop those links.
3. Replace `diagram-static-peer.source.js` with your own relation sources, and the page's title, lede, sections and figures with your own. Rename the page and the source if you wish, and update the `<script src>` reference.
4. Open the page in a browser to see the plates, then run `export-peer.mjs` to write the standalone files you embed.

## What downstream must replace

- The relation sources in `diagram-static-peer.source.js`: ids, presets, titles, labels, relations and wording
- The two declared semantic examples: keep, remove or replace them. Every assignment, figure, `does` and declaration of an example is its author's
- The page's words: the `<title>`, the description, the title and lede, each section, each figure's label, and each figure's `data-columns`, the column names of its relation table
- The file names of the page and the source, if you prefer project-specific names

## What not to edit

- `diagrams-static-peer-engine.js`, `diagrams-static-peer.css`, `export-peer.mjs` and the two generated carriers: re-vendor them byte-identical
- The load order, and the page's figure structure (`.peer-figure` with its `data-spec`, `.peer-host` and the `data-relations` caption)
- The light and dark theme model: the page sets no theme, and `colors_and_type.css` resolves `data-theme` and `prefers-color-scheme`

## Static vs dynamic inheritance

Static diagram artifacts inherit at generation time and freeze for audit. The exporter resolves the Tier 1 + Tier 2 tokens from the local mirror, and a declared semantic example's role values from its systems' stylesheets, and writes them into each file, with the embedded font subset, so an exported plate depends on nothing outside itself. The page takes the same tokens live from the mirror. There is no runtime fetch from the design-system-ASK repo and no font CDN. Re-sync the mirrors and re-vendor the bundle when upstream changes, and re-export.

## Source-truth boundary

design-system-ASK supplies the foundations and the pattern. What the peers are, how they relate, what a relation means and, in a declared semantic example, every assignment and its basis are the consuming project's: a plate illustrates its spec, and the spec's own source remains authoritative. Hosting this scaffold in design-system-ASK does not make this repo the owner of downstream content, and A-S-K and L-E-O-V remain ASK's instances, not the pattern's vocabulary.

## Class A vs Class B

This is Class A (system / architecture diagram templates) — the **peer** grammar. Its static siblings [`patterns/diagram-static-H/`](../diagram-static-H/README.md), [`-V/`](../diagram-static-V/README.md), [`-SEQ/`](../diagram-static-SEQ/README.md) and [`-FLOW/`](../diagram-static-FLOW/README.md) share the `window.DIAGRAMS.render` interface; the interactive [`patterns/diagram-interactive-spine/`](../diagram-interactive-spine/README.md) is a separate Class A pattern. Class B (project-output artifact templates) is [`patterns/output-artifact/`](../output-artifact/README.md) and [`patterns/message-archive/`](../message-archive/README.md). The classes stay distinct. All inherit Tier 1 + Tier 2 from design-system-ASK, but they serve different artifact classes.
