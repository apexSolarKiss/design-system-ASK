# instrument // surface pattern

The machinery around a product's own generated artwork on a live page: a stage that fits a canvas to a chosen frame, three views (docked, full window and fullscreen), PNG saves at fixed sizes, and the layout and controls around them. The product supplies the artwork and one drawing function; the pattern never reads the artwork.

It is a **surface pattern**: a live component a page mounts ([`README.md` §Scope](../../README.md#scope)). A consumer vendors a pinned copy, re-syncs when this contract changes, and seals nothing.

**It is its own page composition, outside [`surface-shell`](../surface-shell/README.md).** Its full-window view takes the whole window, with one row of actions under the canvas, and that cannot sit inside the shell's header and footer. The shell's contract provides for this: a surface describing a different composition "owns that composition outside this generic shell" ([`surface-shell` README](../surface-shell/README.md#consuming-this-pattern)). The instrument uses the same root modules as the shell's pages (`colors_and_type.css`, `surface-action.css`, `surface-panel.css`, `surface-treatments.css`) and is Tier-3-neutral: its head carries the product's name, and the product supplies any mark and browser icon.

## What the pattern owns and what the product keeps

| The pattern | The product |
| --- | --- |
| the drawing contract below; it never reads the artwork | its engine, its artwork and its palette, ground and edges |
| the page layout: head, stage, action row and panel; on narrow screens the stage and actions pin above the scrolling controls | how a work meets a frame: crop to it, or fit inside it |
| the views: docked, full window, and fullscreen with full window as its fallback; Esc leaves full window | its generation and play loops, and undo |
| the frames and their fitting; a canvas drawn at the screen's pixel ratio up to a cap (2 by default, and a pixel budget); a short settle after slow draws | every key other than Esc, and canvas input |
| the saved sizes and the PNG save | its settings in the address and in storage |
| the control presentation: actions, panel, disclosure, selector segments, slider rows, value readouts, status line, screen-reader line | all labels and copy, the filename suffix, and its Tier 3 |
| larger touch targets on a coarse pointer, and a `data-draw` hook for a product that draws with a finger | which canvas takes finger drawing, by setting `data-draw="true"` |

Code two products happen to share beyond this (an announcer, a readout helper, a settings parser) stays in the products.

## The drawing contract

The product passes `render(ctx, width, height, info)`, and the same function draws the live canvas and every save:

- it paints the whole rectangle, ground included;
- it is synchronous, and the same work at the same size gives the same pixels: no random numbers, nothing started;
- it places everything from `width` and `height` inside the call, and reads no window size, pixel ratio or theme;
- it reads the work and never changes it;
- the context arrives in its default state every time.

`info` is `{ purpose: 'view' | 'export', frame, aspect, pixelRatio }`. For a save, `frame` is the frame being saved, which can differ from the one on screen. A view change, a resize, a theme change or a save never asks the product for a new work, only to draw the one it has.

## Frames and saved sizes

| Frame | Shape | Saves |
| --- | --- | --- |
| `free` | the space on screen | 2160 on the short side, the long side capped at 3840 |
| `square` | 1:1 | 2160 × 2160 |
| `four-three` | 4:3 | 2880 × 2160 |
| `wide` | 16:9 | 3840 × 2160 |

These are the instruments' size family, not a rule for other consumers. A save draws off screen at the exact size, one at a time (a save asked for while one runs gets that one's result, whatever frame it names), with a 30-second limit on encoding the PNG, and names the file `<name>-YYYY-MM-DD-HHMMSS[-<suffix>]-<width>x<height>.png`. Nothing on screen changes.

## API

`INSTRUMENT.create(options)` mounts one instrument; `INSTRUMENT.FRAMES`, `INSTRUMENT.contain(w, h, aspect)`, `INSTRUMENT.stamp(date)` and `INSTRUMENT.VERSION` (the contract version, `1`) are also exposed.

**Options:** `root` (the `.inst` element), `stage` (the `.inst-fit` box the canvas is fitted into), `canvas`, `render`; optional `pin` (the block pinned over scrolling controls), `frames`, `frame` (the starting frame id), `name` (the filename's start, default `instrument`), `fileSuffix()`, `formatSize(w, h)`, `maxPixelRatio` (default 2), `maxPixels`, `storageKey` (remembers the frame), `beforeFrameChange(next, current)` (return `false` to refuse).

**The instance:** `version`, `frames`, `frame`, `view`, `metrics`, `context`, `fullscreenSupported`, `lastRenderMs`, `state()`, `bind(elements)`, `setFrame(id)`, `setView('docked' | 'window')`, `setPanel(open)`, `enterFullscreen()`, `exitExpanded()`, `exportSize(frameId)`, `exportPNG({ frame, download, defer, date })`, `pointFromEvent(event)`, `redraw()`, `requestRedraw()`, `refit()`, `on(type, fn)` (returns an off function) and `destroy()`.

**Events:** `resize` (before the redraw that follows it), `change` (with the state and its reason), `export` (the result) and `error`.

**`bind(elements)`** wires the controls every instrument shares, each optional: `frame` (radio inputs whose values are frame ids), `size` (the text of the size a save produces), `save`, `fullWindow`, `fullscreen` (a button or a list), `exit` and `panelToggle`. It keeps their attributes true, and when a control hides while it holds focus, focus moves to its counterpart.

## Markup

The template is the canonical markup. The root is `.inst` with `.inst-head`, `.inst-pin` (stage and action bar), `.inst-stage` holding `.inst-fit > canvas`, `.inst-bar` (status, screen-reader line, actions) and `.inst-panel`. The script sets `data-frame`, `data-view`, `data-expanded` and `data-panel` on the root, `--inst-pin-height` on the root when a pin is given, and `--inst-canvas-width` and `--inst-canvas-height` on the fit box. While expanded it adds `inst-lock` to the `html` element, which stops the page scrolling. Layout classes inside the panel: `.inst-panel-body`, `.inst-col` (`.inst-col--second` for the second group), `.inst-group`, `.inst-row`, `.inst-rule` and `.inst-span`. Controls: `.inst-field` (a caption over one control row), `.inst-seg` (a native radio group drawn as segments; `.inst-seg--two` for two equal columns), `.inst-range` with `.inst-value`, `.inst-note`, `.inst-status`, `.inst-sr`. `.inst-when-expanded` shows only when expanded, and `.inst-wide-only` hides on a phone-width expanded row. Actions are DS compact actions (`.surface-action`), and the panel toggle is the DS controlled disclosure trigger.

## Artwork and chrome

The canvas holds the product's artwork, in the product's colors, in every theme. The DS interface rules govern the chrome and controls around it, and the chrome follows the operating system's light or dark setting. Chrome never sits on top of the artwork: expanded, the controls sit under or beside the canvas on the page field.

The artwork's colors are the product's. The named artwork palettes in [`art-palettes.json`](../../art-palettes.json) are available to it ([`README.md` §Artwork palettes](../../README.md#artwork-palettes)), and a product may use its own ASK-approved palette instead. The instrument neither loads nor requires that file. Python reads it directly, and a served page with `fetch`; a page opened from disk cannot fetch it.

## The canvas focus ring

Keyboard focus on the canvas shows a ring inside the canvas edge, so nothing clips it: an outer 2 px band of `--ask-fg-light` (`#6A637F`) and an inner 2 px band of `--ask-white` (`#FFFFFF`). The ring is in fixed values because the artwork beneath it may be light or dark whatever the theme, and two tones keep it visible on both. An overlay on the fit box, matched to the canvas box, paints both bands; the canvas's own outline paints the outer band too, and is what shows where `:has()` is unsupported.

## Instrument-local departures

These differ from the root modules and stay local to `.inst`. They are not sanctioned variants for any other surface.

| Departure | Why |
| --- | --- |
| Expanded, the stage drops its frame material and the panel its shadow | the canvas takes the window, and nothing is painted over the artwork's edge |
| Selector segments and slider rows | control roles the root modules do not have; local to the pattern |
| On a coarse pointer, an invisible margin on actions (`inset: -5px 0`) and on the disclosure trigger (`inset: -13px 0`), and 44 px segments and sliders | larger touch targets without changing `surface-action.css` or `surface-treatments.css` for every consumer. A comfort choice, not a conformance claim |
| `.inst [hidden]` forces `display: none` | a DS class that sets `display` would otherwise beat the browser's `[hidden]` rule |
| A busy style on the save action, `opacity: 0.6` and the progress cursor | the same values as the radial pattern's export control |
| The two-tone canvas focus ring in fixed values | above |

## Checks

[`tests/instrument.mjs`](../../tests/instrument.mjs) renders the specimen in headless Chrome: frames, views, saved sizes and the frame a save draws for, touch target sizes measured from boxes and margins, and the focus ring on light, dark and plum artwork, with planted faults ([`tests/README.md`](../../tests/README.md#instrumentmjs)). [`tools/check-instrument-neutrality.mjs`](../../tools/check-instrument-neutrality.mjs) keeps product words out of the vendored files; a consumer adds its own with `--deny FILE`.

**Not covered by those checks:** Safari, Firefox, a physical device, a device's save or share flow, native fullscreen where headless Chrome declines it, and a page opened from disk (the checks serve the repository over HTTP). Touch is measured from boxes and margins, not by finger tracing or hit testing. Check the platforms on the standalone specimen, not the gallery's host page, whose frame does not allow fullscreen.

## Consuming this pattern

Vendor `instrument.js` and `instrument.css` byte-identical, with the four root modules and the fonts, at one pin, and re-sync when this contract changes. Start from the template's markup, replace the example script with the product's own, and keep the product's artwork, settings and copy in the product. A product that drew the same artwork before adopting the pattern keeps drawing it: adopting the pattern changes the frame, views and saves around the artwork, not the artwork.
