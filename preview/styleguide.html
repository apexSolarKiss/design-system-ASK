Browser / under-page edge

The area a browser paints beyond the document — the over-scroll pocket above and below the page — plus how it renders scrollbars and form controls. A browser derives the first from a solid background color, not from a gradient, and the second from color-scheme. Both are page-wide, so the foundation owns both on the root. --bg-edge is the semantic role; it binds existing palette values and creates none. It is painted on html beneath the gradient, so nothing visible on the page changes.

--bg-edge—
:root color-scheme—
html background-color—
body background-color—

Use the mode selector above to check all three theme paths. body stays transparent on purpose: the root carries the solid, and the root's background is what propagates to the canvas.

These readouts are necessary, not sufficient. They show the values the browser is being handed. The pocket itself sits outside the viewport and cannot be judged in a desktop window — confirm it on a real device by over-scrolling past the top and bottom of the page in both light and dark.

Textual link unboxed · canonical .surface-text-link

A link inside running prose or a structural title, opted in by class. The resting rule is the emphasis accent at partial opacity — its own hue at a reduced dose, never mixed toward the foreground. Hover raises it to full opacity. Focus is governed separately and independently. The module declares no text color: an ordinary link inherits its context, and a role-colored anchor keeps its own.

This is the default-ASK treatment, and no strict AA claim is made for it. The resting underline measures 1.72:1 and 1.82:1 against the light gradient stops and 2.11:1 and 2.23:1 against the dark — below the strict 3:1 non-text floor in both themes. In light that floor is unreachable at any opacity, full included; in dark a higher opacity would reach it, but that would be a different treatment from the single uniform default. The affordance rests on the presence of a rule where the surrounding prose has none, plus the independently governed focus indicator, which does clear its own requirement. No AA alternate ships in this unit.

The design system is published at design-system-ASK, and the catalog lists every surface and artifact pattern it exhibits.

Semantic color // one physical color, several named questions

Current color assignments read across a row · a shared value is a shared family, never a shared meaning

Each semantic system answers its own question, and its label names that question. Within the named question, green is affirmative, yellow qualified, orange materially undermined and red negative; magenta is a proposal or a requested change. Violet, cyan and magenta name kinds and are never ranked. This is a shared signal, not a universal ranking: supported evidence need not describe a desirable outcome, adverse under one criterion does not reject a whole option, and a declined review can be a sound decision. The visible words carry the role, wherever a color appears.

Treatments // by physical color

Each shared treatment, in each physical color a governed meaning admits, drawn by the module that owns it. Every unit names its color first, then shows the treatment, the roles that draw it there and its availability. Availability is implementation coverage, in the README's application coverage statuses: supported, proposed extension, not implemented and not applicable. It judges no evidence, and it is a separate fact from a color's semantic assignment: brown is a supported physical treatment whose semantic assignment is Unassigned. Tokens and resolved values sit behind each family's disclosure. Painting a color does not admit a meaning.

Four applications of existing treatments, each bound by its own system and drawn here by the modules that bind them. Each keeps its system's words beside its color. None applies inside a multi-axis review annotation, where the square, the dot, the outline, the range and the passage mark stay the channels.

A // Spectral State labels and rails

Context: an architecture description, a figure caption or a table that names an element's state in words, outside a multi-axis review annotation; inside one, the square keeps the state channel. Binding: spectral-state.css binds each chromatic role's value to the label's edge and, through the label at a range's head, to the range's scope rail, with green's, yellow's and red's rail paint for earned, partial and deflated. The words stay in the label role and nothing fills, so no ink is needed. The label names its axis, so a green edge never reads as an accepted review. Neutral takes no keyed label.

State // EarnedState // PartialState // DeflatedState // StructuralState // HeldState // Proposed

Structural or partial. One element at one declared scope shows one primary state. Where operation is established only at bounded depth, the state is partial, and any structural or schema assurance is recorded as its basis. Structural applies where structural or schema assurance is established and operational assurance is not, for that scope. Earned still requires full-depth operational grounding, and different scopes may carry separate labeled records.

B // Evidence State labels and rails

Context: a statement in a report, a figure or a table that records what the available evidence supports about a scoped claim, outside a multi-axis review annotation; inside one, the dot keeps the evidence channel. Evidence State asks what the evidence supports, not whether a claim is true. Binding: evidence-state.css binds each chromatic role's value to the label's edge and the range's scope rail, with green's, yellow's and red's rail paint for supported, partially supported and contradicted; weakened and unresolved keep the plain stroke. The label names its axis. Not yet testable keeps its whole contract, so its standalone form is the existing note: lavender-gray, a dashed rail, a hollow marker and the visible label.

Close pairs, told apart by their words. Green beside yellow, and orange beside red, can read alike for some color vision; a simulation shows it, and a simulation is not user testing. A dot tells an evidence mark from a state square, never one evidence role from another, so the visible words carry Supported from Partially supported and Weakened from Contradicted, on a filled shape and beside a dot alike.

C // A decision record: the panel and the node

Context: a standalone decision record. In a review summary or a status board it is a panel; in a diagram, a decision node. Inside a reviewed document the review mark, the range and the passage mark stay the channels; neither replaces them. Binding: review-semantics.css binds each pending or decided role's Review State value on .review-record. A panel takes it as PERIMETER PAINT's color and as its outcome label's border, and its words keep the theme's text roles; the perimeter blooms alike for all four outcomes. A node, declared with data-record-presentation="node", takes it as FILL PAINT's color, with that color's existing ink as --review-*-ink. Each record states its outcome in words and names, in fields of its own, what it concerns, who decided or decides and the scope, and any material condition. It is inert, and its color confers no authority: a declined record can be a sound decision.

D // Criterion Assessment labels and bounded assessed ranges

Context: a passage in a report or a review that assesses how one characteristic serves one declared criterion, outside a comparison table and a multi-axis review annotation. Binding: criterion-assessment.css binds favorable, caution and adverse to the label's edge and, through the assessment record at a range's head, to the range's scope rail, with green's, yellow's and red's rail paint. The keyed label never stands alone: it heads an assessment record that names the criterion, its direction, the scope assessed and the basis, and the rail ends with the range. One record assesses one contiguous passage under one criterion; a second criterion takes its own record and range, and ranges never nest or overlap. Unassessed takes no label. A color generates no judgment: the example's author assigns each assessment under its stated criterion.

Assessment // Caution criterion // implementation risk direction // lower is better scope // option A's migration path basis // pilot, round 2: 3 of 12 steps wait on a vendor patch

The migration path reuses the existing exporter for every format except SVG, so most of the change stays in code that already ships.

SVG export needs a vendor patch that is not yet released; until it lands, the path depends on a fork the team would maintain.

Assessment // Adverse criterion // set-up time direction // less is better scope // option B, first deployment basis // pilot median 15 min against a 10 min target

Option B's first deployment took a median of 15 minutes across the pilot.

Assessment // Favorable criterion // offline reading direction // fuller access is better scope // option B, an exported copy basis // the pilot's copy opened from disk with no connection

An exported copy of option B opens from disk with no connection.

Two criteria on one option take two records and two ranges. An adverse assessment can sit beside supported evidence: Evidence // Supported would say the pilot's 15-minute median holds, and the adverse assessment says that median works against the set-up criterion. The comparison table keeps its own cell-local rails and takes no record: rail family 3, above.
